# GitHub Issues 执行清单

版本化文档是规格真源；Issue 是执行队列。Fork 建立后为阶段 0—5 各建一个父 Issue 和同名里程碑，父 Issue 链接对应阶段文档。以下每一行建立一个子 Issue，标题以编号开头；用 GitHub 依赖关系表达“前置”。每个子 Issue 使用 [Research 任务模板](../../.github/ISSUE_TEMPLATE/research-implementation.yml)，引用对应阶段文档的任务编号，不复制整篇文档。GitHub 支持[子 Issue 与依赖关系](https://docs.github.com/en/issues/tracking-your-work-with-issues/learning-about-issues/about-issues)。

每个子 Issue 只给一个轻量模型执行；合入前须按模板填上准确的允许修改范围、验收命令和实际结果。一个 PR 关闭一个子 Issue。阶段父 Issue 只有在阶段出口和所有子 Issue 都验收后关闭。阶段 0 为 `BLOCKED` 时，正文相关 Issue 保持阻塞；可以继续文档、本地模拟或已确认允许的元数据任务。

## 单项任务工作量边界

一个子 Issue 对应上表一个交付物，优先限制在一个子系统、一次可核对的 PR。若执行时发现必须改动另一阶段的契约、公共接口或上游 Core，先在 Issue 写出证据与拟议变更，让主线程更新契约和依赖后再继续；不要在当前 Issue 中顺手扩展。Review 使用阶段文档的出口条件核验，而非仅看代码能运行。

## 创建顺序与标签

先建立阶段 0 父 Issue 与四个子 Issue。阶段 0 结论确定后再创建或激活后续阶段子 Issue，避免把受阻任务误派出去。建议标签仅用 `phase:0`—`phase:5`、`blocked`、`docs`、`code`；阶段用里程碑、父子关系表达，不另建 Projects 看板。创建时把表中编号依赖转换为 GitHub issue dependency，PR 正文引用子 Issue 并附验收结果。
